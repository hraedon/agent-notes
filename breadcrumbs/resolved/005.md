The `file_breadcrumb` MCP tool schema documents `file_path` as "Canonical relative path (overrides auto-computation)" and the handler forwards it into `BreadcrumbModel.file_breadcrumb(..., file_path=...)` (servers/breadcrumbs.py:500,516). But `_write_projection` (servers/breadcrumbs.py:82-99) then unconditionally recomputes:

    status_dir = _status_to_dir(row["status"])
    new_file_path = f"{status_dir}/{identifier}.md"
    old_file_path = row.get("file_path") or new_file_path
    if old_file_path != new_file_path:
        # ...update DB to new_file_path

The user-supplied override is briefly stored on the row, then clobbered by the status-derived path before projection is written. Observed in session 2026-05-21: passed `file_path="open/001-omnibus-tool-name-collision-silent-first-wins.md"` (status=open), got `breadcrumbs/active/001.md` (status `open` maps to `active/` via _status_to_dir).

Two distinct issues:
1. **Tool schema lies.** Plan §6 explicitly says: "Removed: file_path parameter on file_breadcrumb. Derived from projects.breadcrumbs_dir." The MCP tool registration (servers/breadcrumbs.py:~261) still advertises the param. Schema and behavior must agree.
2. **Naming convention loss.** The status-derived path uses bare `<identifier>.md` (e.g., `active/001.md`), losing the human-readable slug suffix that substrate/sf2 use (`184-hook-queue-depth-metric-missing.md`). Whether or not file_path overrides are restored, the auto-computed path could include a slug derived from the title.

## Resolution

Resolved in Phase 8a (Plan 003). The entire markdown projection layer was removed: `core/projection.py`, `_write_projection`, `_status_to_dir`, `file_path` column, and the `breadcrumbs_dir` project attribute. The DB is now the sole source of truth (decision 39). `file_path` no longer appears in the `file_breadcrumb` tool schema.
