## Resolution

Fixed in `src/agent_notes/servers/breadcrumbs.py` via `_write_projection`:
- Added an early guard: if `project.breadcrumbs_dir` is unset, the projection write is refused with a clear error message:
  `Error: this project has no breadcrumbs_dir configured. Run \`agent-notes init <path>\` to register the project, then re-file the breadcrumb.`
- The DB row is still written (breadcrumb is not lost) so the caller can run `init` and update the projection in a subsequent call.

This removes the silent `/tmp/active/` fallback entirely.

## Also delivered

- `agent-notes init <path>` CLI (decision 32) added to `src/agent_notes/cli.py` and `src/agent_notes/scripts/init_project.py`
- `resolve_project(path)` core helper added to `src/agent_notes/core/db.py`

## Observed (historical)

Calling `file_breadcrumb` against `project=substrate` succeeded and returned:

    Breadcrumb filed: **197** (design / proposed) in project substrate
    Projection written: /tmp/active/197.md

The breadcrumb was correctly persisted in the agent-notes database, but the projection file landed in `/tmp/active/197.md` rather than `/projects/substrate/breadcrumbs/`. The substrate project's on-disk breadcrumbs (resolved/ + numbered active files + README index) live under `/projects/substrate/breadcrumbs/`, and 195/196 were filed directly to that location by hand. 197 silently diverged because the MCP wrote it elsewhere.

## Why this matters

The agent-notes-mcp value proposition assumes the database and the on-disk projection stay in sync — operators read the on-disk index (README + `<id>-<slug>.md` files) when offline, in code review, and during the /end skill's commit step. A breadcrumb filed via the MCP that does not appear in the project's tracked breadcrumbs directory:

- Is invisible to humans reading the repo.
- Is not committed by the /end skill or any project-level git workflow.
- Drifts from the on-disk index (README "Open" table won't list it).
- Will be silently lost if `/tmp` is cleaned by the OS.

The failure is silent in the sense that the tool returns success and reports a path; nothing surfaces "this project has no configured projection root, falling back to /tmp."

## Suspected root cause

Per BC-005's discussion of `_status_to_dir` and `projects.breadcrumbs_dir`: when a project row exists but `breadcrumbs_dir` is NULL/unset (or when the project is auto-created on first reference without that column being populated), the projection writer appears to fall back to a default like `/tmp/active/` rather than refusing to write or warning loudly.

The `mcp__breadcrumb__list_projects` output for `substrate` shows the row exists (`workspace_id=4`) but does not display a `breadcrumbs_dir` value, suggesting the column is unset for projects that weren't explicitly registered with their on-disk path.

## Proposed fix

Choose one of:

1. **Refuse to write projection when `breadcrumbs_dir` is unset.** Return an error like `PROJECT_NOT_CONFIGURED: project 'substrate' has no breadcrumbs_dir; register the project with its on-disk breadcrumbs root before filing.` Database row is still written (so the breadcrumb isn't lost), but the caller is told the projection step failed and given the remediation.

2. **Auto-detect breadcrumbs_dir from a conventional location.** If `breadcrumbs_dir` is unset, look for `/projects/<project>/breadcrumbs/` (or whatever the repo-discovery convention is) and use it if present. Persist the discovered path so subsequent calls are consistent.

3. **Surface the fallback loudly.** If the tool *must* keep its current /tmp behavior, change the success message to a clear warning: `WARNING: projection written to /tmp/active/197.md because project has no breadcrumbs_dir configured. This file will not be tracked by the project's repo.`

(1) is the safest; (2) is the most user-friendly if the discovery convention is reliable; (3) is a stopgap that at least eliminates the silent failure.

## Acceptance criteria

1. Filing a breadcrumb against a project with no `breadcrumbs_dir` either:
   - returns an error and does not write a projection (option 1), or
   - writes the projection to a discovered on-disk location matching the project's repo convention (option 2).
2. In no case does the tool report success and write to /tmp without a prominent warning in the response.
3. `mcp__breadcrumb__list_projects` output exposes `breadcrumbs_dir` (or its absence) so callers can verify configuration before filing.
4. Documentation or `AGENTS.md` describes how to register a project's `breadcrumbs_dir` and what the discovery convention is.

## Workaround used in this session

Manually `mv /tmp/active/197.md /projects/substrate/breadcrumbs/197-no-delegation-chain-agent-actor-cannot-bind-to-human.md` and edited `/projects/substrate/breadcrumbs/README.md` to add the row. The database row exists with the original `/tmp/active/197.md` `file_path`, so projection state is now drifted from the on-disk reality — `reconcile_projection` on identifier 197 would likely overwrite the moved file (per its docstring warning).
