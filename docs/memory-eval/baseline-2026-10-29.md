# Memory recall baseline, 2026-10-29 (Plan 027 Phase 0)

**Status:** first baseline. **The labels are a Claude draft
(`labeler: "claude-draft"`) and need owner review.** A second, independent
labeling pass (Codex) is a follow-up; until both exist, treat every number
here as provisional.

## Method

- **Fixture:** `tests/memory_eval/fixture.jsonl`, 33 queries across 18
  projects. Each names the memories a good answer should include
  (`relevant`) and the ones that would be outdated or harmful
  (`stale_or_wrong`). Every expected name was checked to exist with
  `active = true` in the frozen snapshot
  `tests/memory_eval/names-snapshot-2026-10-29.json` (59 names; 511 active
  rows of 582 at snapshot time).
- **How the queries were found.** They come from real work in the production
  DB, read with SELECT only: recent work-item titles in each project, then a
  keyword search over memory names and bodies to find which memories answer
  each query and which ones contradict later state (work-item status, a later
  memory, or `AGENTS.md`). The labels were **not** derived from the ranker
  under test.
- **Runner:** `scripts/eval_memory_recall.py --command both`, run on mvmcc02
  against agent-notes 1.1.1 (native engine). Each query calls `agent-notes
  memory search` and `agent-notes memory recall` with `--scope composed
  --workspace default --project <slug> --limit 10 --json` in a subprocess.
  Both commands are read-only; the script refuses any other subcommand.
- **Metrics** (k = 5):
  - `P@5`: relevant names in the top 5, divided by 5.
  - `nP@5`: the same, divided by min(5, |relevant|). Most queries have one or
    two relevant names, so raw P@5 is capped near 0.2–0.4; nP@5 is the more
    readable number.
  - `MRR`: 1 / rank of the first relevant name within the top 10.
  - **Stale-hit rate:** the share of top-5 slots that hold a `stale_or_wrong`
    name or a row reported inactive. The CLI filters `active = true`, so
    inactive rows can't appear; staleness here comes from the labels.
  - **Reflection outranks fact:** among queries where a relevant
    non-reflection memory is returned, how often a non-relevant reflection
    ranks above it.

Queries with no relevant label (q24, q28, q29: "no current memory answers
this") count only toward the stale metrics.

## Observations

1. **When a distilled fact exists, retrieval finds it.** In 22 of the 26
   fact-backed queries, the fact is at rank 1 (scores 0.73–0.89, median
   0.81). The fixture is biased towards this: its queries were found by
   keyword search over memory bodies, so they share vocabulary with their
   targets. Treat 0.92/0.86 as an upper bound, not as typical session
   performance.
2. **Stale memories are retrieved as confidently as current ones.** In 6 of
   the 8 queries with a labelled stale memory, that memory is in the top 5.
   - Where no current memory exists (q28 `project-initiation-skill-needed`,
     q29 `family-editable-installs`), the stale fact is **rank 1 with a score
     of 0.77**, and nothing in the result marks it as outdated.
   - `active` + `supersedes` didn't help, because nobody superseded them.
     These are exactly the cases the Phase 1 hygiene report (age plus
     contradiction) and a `contradicts` link (WI-1.2) are meant to catch.
3. **Reflections crowd the result list.** They take 61% of top-5 slots.
   - In q05, a 2026-06-20 reflection saying "CI only tests 3.12" ranks 1st,
     and the fact that closed WI-036 with a 3.12–3.14 matrix ranks 9th.
   - Where a project has only reflections (cert-watch: 96 of them, no facts),
     the right answer is buried among near-identical session summaries (q27:
     1 of 5 relevant in the top 5, MRR 0.2).
   - Reflection outranks fact is only 11.5% overall, but its failures are the
     harmful kind (q05).
   - This supports WI-1.3 (rank reflections below facts), and suggests
     distillation for reflection-only projects.
4. **The one global memory pads every small project.**
   `reference-playwright-mcp-browser-pin` appears in the top 5 of 11 queries
   where it is irrelevant (scores 0.49–0.60). In q13 it ranks **above** the
   correct project memory (0.53 vs 0.38). The composed search has no score
   floor, and short project lists are padded with whatever is nearest.
   A floor around 0.6 would remove most of this noise but would also have
   dropped q13's correct answer, so any threshold needs this fixture to
   check it.
5. **`recall` adds nothing over `search` on the native engine.** Rankings
   were identical. Each call costs ~10 s, almost all of it loading the
   embedding model in a fresh process; an agent asking three questions pays
   about 30 s.

## Caveats

- **Labels are a single Claude draft** and need owner review; an independent
  Codex labeling pass is a follow-up. Specific uncertainties:
  - q15: is the vitrine link-checker reference a proposal or a description of
    the committed workflow?
  - q19, q25: these mention regista, which Plan 026 retires; are they still
    current?
  - q22: should the RFC-032 body count as relevant, or as misleading without
    the feedback memory?
  - q24, q27, q29: staleness was inferred from work-item status
    (dossier WI-021 done; cert-watch WI-122/WI-126), from `AGENTS.md`, and
    from WI-074, not from asking the owner.
  - q28: "a project-initiation skill exists" is inferred from the openbia
    and dossier project memories.
- **Selection bias.** Queries were picked where a keyword search found an
  answer, so recall is overstated. Queries whose answer lives only in code,
  `AGENTS.md` or harness-native memory aren't represented. The 33 queries
  span 18 projects, but sf2, v1 and substrate (mostly bulk-imported docs)
  are barely covered.
- **Small n.** One or two queries flip most rates by 3–12 points.
- **Composed scope on mvmcc02:** repo + `vm:mvmcc02` (empty) + global (one
  memory). Results from another VM would differ only if its VM tier had
  rows.
- The stale metric can't see rows that are active but wrong unless they are
  labelled. Inactive rows never appear because the CLI filters them out.

## Reproduce

```bash
export PATH=$HOME/.local/bin:$PATH   # on mvmcc02
python scripts/eval_memory_recall.py --fixture tests/memory_eval/fixture.jsonl \
  --command both --json-out /tmp/memeval.json
```

The text summary goes to stderr and the full per-query JSON to `--json-out`.
Before comparing against this baseline, check that every fixture name is
still active, using the snapshot: renamed or superseded names will show up as
misses.
