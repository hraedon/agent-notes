## On the project

The Plan 008 kernel is genuinely solid. The op-CRDT model (op_log + content_blobs + fold into work_items cache) is clean, the status lattice is fail-safe, and the cross-project layer (derived index + registry + trigger loop) composes without breaking the single-writer path. The Tier A/Tier B boundary is well-drawn — the coordinator-absent default mode is the right posture for the tool's actual adoption reality.

One thing that feels slightly awkward: the `breadcrumbs` table still exists as a safety net alongside the migrated `work_items`. The plan says "can be dropped after verification" but there's no explicit verification step or cut-over command. This is fine for now (the migration is idempotent), but at some point the dual tables will confuse new contributors. The `doctor` check still audits `breadcrumbs` for dangling links, which is correct during transition but will become misleading once work-items fully own the graph.

## On the work done

The trigger loop was the biggest piece. It reuses the bridge's HTTP signing logic (which is good — one transport contract) but adds a new routing layer that queries the DB for reverse edges. I feel good about the routing rules:
- `request.created` → target project's wake channel (project registry lookup)
- `link.added` (cross-project) → target as `dependency.blocked`
- `item.closed` → reverse-edge lookup on both `links` and `cross_project_links` → `dependency.resolved`

The test coverage is thorough: 13 tests covering routing functions, LISTEN/NOTIFY plumbing, and end-to-end `_process_event`. The one thing I'd want eyes on: the `item.closed` routing does two separate queries (same-project links + cross-project links) and could be batched into a single UNION query for efficiency at large scale. For now, it's fine — the target set is usually small.

The fix to `add_cross_project_link` (allowing foreign targets) was a necessary correction. The original implementation raised `ValueError` when the target project wasn't in the local DB, which defeated the whole point of cross-project linking. Now it stores the edge in `cross_project_links` (slug-based, foreign-safe) and mirrors into `links` only when the target exists locally. This is the correct design.

The systemd unit files (`deploy/agent-notes-trigger-loop.service`, `deploy/agent-notes-requeue.service`, `deploy/agent-notes-requeue.timer`) are minimal but sufficient. They use `%i` for the user, which is a systemd template parameter — whoever deploys them should know to instantiate with a specific user.

## Gaps to flag

- `src/agent_notes/trigger_loop.py:76` — `_post_with_retry` is shared code with `bridge.py`. Consider extracting a common HTTP transport module to avoid duplication.
- `src/agent_notes/core/work_item_model.py:1053` — `add_cross_project_link` now stores in `cross_project_links` first, but if the target is local it also mirrors into `links`. There's a race: if the target project is deleted after the link is created, the `cross_project_links` row stays but the `links` row is orphaned. No cleanup is wired. Acceptable for now because project deletion is rare and manual.
- `tests/test_trigger_loop.py` — no test for the `requeue_expired` daemon path. The systemd timer is documented but the actual CLI command (`work-item requeue-expired`) is already tested elsewhere.
- The `agent_notes_changes` NOTIFY trigger still fires on the old `change_log` table. The new `op_log_events` table has its own trigger (`op_log_events_notify`). Both channels exist simultaneously. This is intentional (backward compat) but could be noisy if both the bridge and trigger loop are running — they listen on different channels (`agent_notes_changes` vs `agent_notes_op_log_events`), so no double-delivery.
