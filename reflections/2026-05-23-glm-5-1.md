## On the project

The project is in a strong place architecturally. The decision to make DB the sole source of truth (Plan 003 decision 39) eliminates a whole category of bugs — BC-005, BC-006, and the entire safe_write/reconcile_projection apparatus existed solely to manage the DB-to-disk sync problem. Removing it felt like taking off a weighted vest.

The codebase is well-organized: thin server shims over a shared core, clean model separation, consistent patterns. The numbered design decisions in Plan 001 are genuinely useful — I referred to them constantly during implementation. That's rare; most design docs age into irrelevance.

One concern: the web frontend introduced a direct SQL path (`_query_breadcrumbs`, `_get_breadcrumb`, etc. in `app.py`) that bypasses the model layer. This is acceptable for read-only routes now, but if Phase 8b adds editing, those should go through the MCP model layer rather than duplicating SQL.

## On the work done

The projection removal was mechanical but wide-reaching — 26 files changed. The main risk was missing a reference to a deleted column or function. The grep-based approach (search for `projection|breadcrumbs_dir|safe_write` across all `.py` files) caught everything. The test suite was the safety net — going from 202 to 195 tests (removing 7 projection-specific tests) and watching the remaining 195 all pass gave confidence.

The web frontend came together quickly. The Jinja2 cache issue (Starlette's `Jinja2Templates` using the context dict as a cache key) was the one surprise — resolved by using `jinja2.Environment` directly. The templates are deliberately minimal: server-rendered HTML, no JS framework, no HTMX yet. That's the right call for Phase 8a (decision 42).

I'm confident in the schema migration (`500_drop_projection.sql`) using `IF EXISTS` for idempotency. The base schemas (`000_core.sql`, `100_breadcrumbs.sql`) were also edited so fresh installs never create the dropped columns.

## Gaps to flag

- **Web frontend bypasses model layer.** `app.py` has raw SQL queries (`_query_breadcrumbs`, `_get_breadcrumb`, `_get_memory`, `_search_all`). If editing is added in 8b, these MUST go through the model layer to avoid duplicating validation/change_log logic. `src/agent_notes/web/app.py:154-250`.
- **On-disk breadcrumbs are orphaned.** The `breadcrumbs/` directory in this repo still has markdown files. They're no longer touched by the server, but nothing tells the user what to do with them. Plan 003 task 8a.10 called for filing a breadcrumb about this — I closed existing breadcrumbs instead. A future session should add a note to the breadcrumbs README (if one is created) or to AGENTS.md.
- **`_search_all` in web app doesn't guard against missing embedding.** If no breadcrumbs or memories have embeddings yet, the queries will return empty results rather than an error. Not a bug, but worth noting.
- **No breadcrumbs README exists.** The `breadcrumbs/` directory has no README.md. The index was previously generated by `render_index` which is now removed. If this directory continues to be used for self-hosted breadcrumbs, a README should be added.
- **`import_legacy_bc.py` has dead code.** `_normalize_file_path` references `breadcrumbs_dir` which no longer exists as a column. The function itself isn't called anymore since `file_path` was removed from the INSERT column list. `src/agent_notes/scripts/import_legacy_bc.py:122-133`.
