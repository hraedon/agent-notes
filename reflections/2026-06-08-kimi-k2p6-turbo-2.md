## On the project

The codebase is solid. The `WorkItemModel` → `BreadcrumbModel` mirroring means the migration script is essentially a mechanical transform: read rows, store blobs, emit `create` ops, fold. The content-addressed blob layer is the right design — the migration never re-logs a body, it just hashes it.

One thing that feels slightly off: the `breadcrumbs` table is left untouched by the migration. This is the right safety move (the plan says to leave it as a safety net), but it means the database now has two parallel tables for the same concept. The migration is intentionally one-way and the old table is not dropped. After a few successful migrations, a cleanup PR should drop the old table and retire the `BreadcrumbModel` class.

The degrade contract is simple but correct: `coordinator-absent / local-lease` is the default, and `is_distributed_claim_available()` always returns False until the regista coordinator is actually wired. This means the code is honest about what it does — it doesn't claim to have a coordinator when it doesn't.

## On the work done

The migration script was the most complex piece. The status mapping from `bc_status` to `wi_status` is straightforward but the `closed_at` handling was tricky — the original `breadcrumbs` table doesn't have a `closed_at` column in the same way `work_items` does (it's managed by the `wi_status_changed_fn` trigger). The migration had to set `closed_at` for terminal statuses so the trigger would fire correctly on the new table. The test caught this (the `resolved → closed` test failed until I added the `closed_at` logic).

The skills update was mechanical but tedious — 5 files, each with multiple references to `breadcrumb` and `BC-`. I should have written a small script to do the bulk replacement, but the manual edit let me review each change for context. The `find-breadcrumb` skill was the most subtle — it searches for `breadcrumbs` array in JSON output, but the work-item CLI returns `work_items` instead.

What I'd want a second pair of eyes on:
- The `coordinator.py` module is small (40 lines) but it's the contract boundary. The `check_coordinator_health()` function returns `(False, "...")` for both absent and configured-but-not-integrated cases. Is that the right signal? The plan says the coordinator-absent case is "not a failure" — it's the normal state. So returning `False` from `check_coordinator_health()` might be misleading if someone interprets it as "unhealthy." But `doctor` prints it as PASS because the mode is always valid. The function is only used by `doctor` today; if it gets used elsewhere, the semantics may need refinement.

## Gaps to flag

- **Missing test:** `test_coordinator.py` only tests the mode-detection layer. It doesn't test the integration with `WorkItemModel.claim_work_item()` — the model uses the local lease table regardless of coordinator mode. When the coordinator is eventually wired, the model layer needs to check `is_distributed_claim_available()` before falling back to local lease.
- **Schema drift risk:** The `breadcrumbs` table is still present in the schema. If the migration script is run and then someone adds a new column to `work_items`, the migration script won't know about it. The script should be kept in sync with the `work_items` schema or a view-based migration should be considered.
- **Dead code:** `cmd_bc_query` in `cli/breadcrumbs.py` is still present (filed as BC-018). The work-item CLI doesn't have a `query` subcommand. This is intentional per the reflection, but the dead code is still in the repo.
