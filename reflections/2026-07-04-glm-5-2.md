## On the project

The agent-suite blueprint is an ambitious but coherent target: six components, one spine (regista), auditable agent work as the value prop. agent-notes' role as "the agent face" is well-scoped by Plan 017 — it does not need to solve multi-harness credential brokering or attestation; it needs to (a) read shared config, (b) install its harness wiring repeatably, (c) report health in the common shape, (d) finish the cutover. (a) and (b) were already done (WI-1.1/WI-2.1); this session closed (c) and the docs half of (d). The plan's "do A→B→C and stop to evaluate" advice in the blueprint is sound — the irreducible core is store + two faces + provenance, and agent-notes' MVP contribution is now the doctor contract so a suite-doctor umbrella can aggregate it.

The codebase is mature and well-documented. The doctor script had accumulated 8 checks over many phases but no machine-readable contract surface — exactly the hodgepodge the blueprint targets. The fix was additive and low-risk.

## On the work done

**What went well:** The suite contract shape was straightforward to implement on top of the existing per-check helpers; the tristate `reachable` (None/True/False) cleanly encoded "degrade mode is not a failure, configured-but-unreachable is." Two-round adversarial review earned its keep — the first round caught a **blocking** test-hermeticity bug (conftest cleared legacy `AGENT_NOTES_REGISTA_*` aliases but not the canonical `REGISTA_*` suite vars the resolver actually prefers, so a host with `REGISTA_DSN` set would enable regista for every test) and several majors (DSN-password leak via `str(exc)`, `degraded` status being unreachable, suite checks missing from the human-readable path). The second round confirmed all blocking/major findings resolved and surfaced only low-severity nits.

**What I'm less sure about:** The `_check_chain_ok` semantics. agent-notes owns its own `op_log` (the native chain); regista is a write-through face that replays it into the spine. So `regista.chain_ok` reporting the op-log chain is defensible — it's the chain agent-notes is responsible for — but the field name in the suite contract is literally `chain_ok` under the `regista` block, which a reader might interpret as "regista's own event-log chain verified." I documented this honestly in the docstring and the plan log rather than pretending agent-notes can reach regista's internal chain (it can't; that's regista's own doctor job). A future second opinion from a different model lineage would be valuable here.

**The `degraded` status call.** I chose `degraded` to mean "healthy but spine absent" so the umbrella gets a distinct signal. An alternative reading is that degrade mode is so first-class it should just be `healthy`. I went with `degraded` because the blueprint frames the spine as the suite's value prop and a spine-absent deployment is genuinely not the full-suite posture — but it's a judgment call worth revisiting once the umbrella exists and we see how operators react.

## Gaps to flag

- **`doctor run()` vs `run_json()` divergence on prereq failure.** When DSN/schema fail, `run()` returns early and skips the suite-layer checks (chain/skills/harness/regista-reachable), but `run_json()` runs skills/harness/regista-reachable regardless. Intentional (the human report fast-fails), but worth a comment in `run()` — a reviewer flagged it (`doctor.py:668-680`).
- **`test_doctor_clean_exit_code` doesn't assert the new section headers** ("Op-Log Chain Integrity", "Skills Installed", etc.) — they could be silently removed without the test failing (`tests/test_doctor.py:71-77`).
- **`_check_chain_ok` empty-log case returns `True`** ("fresh install, no violations") which is reasonable, but if an operator expects `null` for "no data," the umbrella logic needs to know an empty chain reports as healthy/valid, not unknown.
- **No enforcement that the editable regista source matches `SUITE.lock`.** The lock is advisory today; nothing in CI/Makefile validates the sibling checkout SHA. Easy to add, not yet added.
- **`deploy/SUITE-INSTALL.md` uses `pip`** but the dev workflow is `uv`-based (`[tool.uv.sources]`). A pip-only operator hitting PyPI for `regista` (unpublished) would fail. The doc notes the editable assumption but a `uv` equivalent would be clearer.
- **`_check_regista_face` detail leaks the project slug** in the JSON detail string — not a secret, but the only check that embeds a config value. Consistent with the existing human-readable output; flagging for awareness.
