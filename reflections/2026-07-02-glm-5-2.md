## On the project

The work-item model has reached the size where it needed surgery, and the codebase handled it well — the regista/native dual-path dispatch pattern is regular enough that the split was mechanical, and the test suite (625 tests, ephemeral-Postgres-backed) gave high confidence that behavior was preserved. The project's discipline around `plans/` documents as the authoritative changelog (CHANGELOG.md lags to release boundaries) is working: I could trace every design decision back to a numbered plan. One thing that keeps biting: CI triggers only on `main` pushes / PRs to `main`, so pushing to a feature branch alone gives no signal — you have to open a PR to get validation. That's fine but worth remembering.

## On the work done

The refactor itself went cleanly — I read the whole 2,189-line file first, then split by concern into free-function modules, keeping `WorkItemModel` as a pure dispatch facade. The one cert-watch-style anti-pattern I found (a test reaching into `WorkItemModel._mirror_regista_snapshot`) I fixed by pointing the test at the explicit `_common` helper rather than propagating the private-name coupling. The adversarial review was the most valuable step: the reviewer flagged 9 items, but it could only diff against the older committed `HEAD` (1,937 lines), not the working tree (2,189, which carried uncommitted review-gate work). I verified all 9 against the true pre-edit source and confirmed every one was faithfully-preserved pre-existing behavior — not regressions. The lesson: an adversarial reviewer without the original to diff against will report faithful reproductions of quirks as drift; you must reconcile each finding against ground truth, not just trust the list.

I'm confident in the refactor's correctness (tests + adversarial reconciliation + the change is purely structural). Less confident in the commit bundling: I committed the feature and the refactor together because they were entangled in one file (the subpackage contains the review_transition code, which depends on `reviewer_actor` from the feature). A cleaner history would have separated them, but reconstructing the intermediate monolith-with-review-code state was too error-prone to justify. The single commit with a two-section message was the honest compromise.

## Gaps to flag

- **`core/work_item/_native.py:388` (`attest_gate_waiver`)** — accepts `actor_id` param but ignores it, always uses `default_actor()`. Latent misattribution if any caller relies on the param. Filed BC-029.
- **`core/work_item/_native.py` claim/release/heartbeat** — no `write_change` calls; regista path writes them. Degrade-mode lease actions are invisible in the audit trail. Filed BC-027.
- **`core/work_item/_native.py:delete_work_item`** — doesn't delete from `work_item_leases`; regista path does. Orphaned leases can distort `claimable`/`ready` queries. Filed BC-028.
- **CI trigger config** (`.github/workflows/*.yml`) — only runs on `main` push / PR-to-`main`. Feature-branch pushes give no signal; contributors must open a PR to validate. Noted but not changed.
- **Commit history entanglement** — the review-gate feature and the module split share one commit because the refactored subpackage references `reviewer_actor` from the feature. A future contributor bisecting will see both move together; the commit message documents this.
- **Adversarial reviewer limitation** — the kimi reviewer lacked bash/git access, so it diffed against stale `HEAD` and reported pre-existing uncommitted features as "drift." When dispatching adversarial reviewers on a dirty working tree, give them the pre-edit content explicitly or they'll false-positive on the uncommitted work.
