## On the project

agent-notes is the suite's agent face, and Plan 017 is where it stops being a
solo tool and starts being a suite component — one config contract, one
bootstrap command, one health shape. The architecture is genuinely coherent for
this: `core/config.py` already had the harness-independent config-file fallback
(Plan 012 WI-1), so adopting the canonical `REGISTA_*` names was a clean
precedence change, not a rewrite. The harder, more interesting tension is that
the suite install-harness *contract* assumed opencode.json has an env block —
it doesn't (`additionalProperties: false`, verified against the live schema).
The codebase's existing config-file fallback turned out to be exactly the right
escape hatch. That's a sign the earlier Plan 012 decision was correct: the
config file exists *because* non-interactive launchers skip ~/.bashrc, and that
same property makes it the correct opencode env target. One paragraph of
architecture paying off twice.

What feels fragile: the opencode config schema is an external dependency. If
opencode adds an `env` key later, the D1 decision should be revisited, but
nothing in the code flags that. The plugin path resolution is repo-relative
(not package-relative), which works for the editable-install deployment but is a
latent break for a published wheel.

## On the work done

WI-1.1 was straightforward and I'm confident in it — the precedence chain
(canonical > legacy-warn > file) is clean, the one-shot deprecation guard is
simple, and the 11 new tests cover the overlap matrix. The two admin scripts
now route through `regista_config()` so the whole CLI surface reads suite.env.

WI-2.1 was the bulk of the work and where the real complexity lives. The
manifest-tracking design (D2) went through three iterations: first "track
newly-written keys" (broke on re-install — the manifest blanked), then "track
managed = newly + already-matching" (broke the no-clobber case — a user's
pre-existing matching value would be removed on uninstall), finally "track
managed = newly + (matching ∩ prev-manifest) + (prev-managed still-present)".
That last form is correct but non-obvious; I'd want a second pair of eyes on
the `_install_harness_one` preservation loops specifically. The adversarial
reviewer (same model — honest about that limitation) caught the
manifest-drift-on-reduced-env case that my second iteration missed, which is
exactly the kind of bug that surfaces months later as a stale DSN.

What I'm less sure about: the `no_op` calculation. It works on the tested paths
but the interaction between "kept existing (no clobber)" actions and `no_op`
is defensible-but-arguable — a no-clobber conflict makes `no_op: false` even
when nothing was written. A bootstrap script keying on `no_op` might be
surprised. I left it because "not fully wired" is a fair characterization, but
it's a judgment call.

## Gaps to flag

- **`_plugin_path()` / `_repo_skills_root()` are repo-relative** — broken for
  pip (non-editable) installs; `pyproject.toml` doesn't declare
  `integrations/` or `skills/` as package data. Pre-existing (inherited from
  install-skills) but install-harness makes it worse by writing a broken
  plugin path to opencode.json. Filing was blocked by the pending regista
  migration; needs a BC filed next session. `cli/harness.py:105`,
  `cli/skills.py:24`.
- **`_save_json` is non-atomic** — truncating write, not temp+rename. A signal
  mid-write could corrupt `settings.json` (which holds DSNs with passwords).
  Pre-existing pattern (`cli/__init__.py` does the same) but install-harness
  writes to more files. `cli/harness.py:146`.
- **`_WARNED_LEGACY` one-shot guard is not thread-safe** — benign (warning
  fires twice under contention instead of once) but the web frontend
  (`agent-notes-web`) could trigger it from concurrent request threads.
  `core/config.py:60`.
- **opencode `--user` is a warned no-op** — principal_id resolves from git
  config per `core/actor.py`. Documented as deferred to WI-4.2, but a caller
  passing `--user` to `install-harness opencode` gets a stderr warning, not an
  error. Intentional.
- **regista structlog lines leak to stdout on `work-item file --json`** —
  this is the known WI-019 regression; it broke my breadcrumb-filing JSON parse
  this session. Still open.
