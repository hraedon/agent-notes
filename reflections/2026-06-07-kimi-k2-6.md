## On the project

The codebase is in a good state — DB-canonical, test-driven, and the conventions are consistent. The `BreadcrumbModel` → `WorkItemModel` mirroring worked well; the CLI pattern is established enough that adding a new kind is mostly mechanical. The content-addressed blob layer is a clean win over the old `body` column: metadata edits no longer re-log the body, and the `work_items` cache stays small.

One thing that feels slightly off: the `op_log` and `change_log` tables coexist. The `change_log` table is still the source for the `change_log_notify_fn` trigger and the `agent_notes_changes` channel. The `op_log` is the new source of truth, but `op_log_events` is a separate table. This is correct for P0 (the trigger is untouched), but the migration from `change_log` → `op_log` as the sole audit source is going to be a nontrivial piece. The plan says migration is its own PR before P0 — so this tension is intentional, not a mistake.

## On the work done

The kernel module (`kernel.py`) is the load-bearing piece. I'm confident in the `commit_op` / `fold_work_item` / `store_blob` primitives. The `op_id` is a content hash of the canonical payload, which gives deterministic identity. The `entity_id` is the hash of the first op, which is also the hash of the `create` payload — this is the right design per the plan.

The `ready` view (`work_items_ready_v`) is a single SQL query against the folded cache and the existing `links` table. It correctly excludes deferred and blocked items. The test for blocking (`test_ready_excludes_blocked`) passes. The `claimable` view is identical to `ready` for P0 — the plan explicitly says P4 adds the lease table.

The DSSE envelope module (`envelope.py`) is structurally correct but entirely unverified in P0. The `NullSigner` emits `UNSIGNED` as the signature. This is the right tradeoff — the envelope format is present from day one, and flipping to `LocalKeySigner` in P1 is just a config change. However, the `cryptography` import is optional ( guarded by try/except ) and the `LocalKeySigner` key path uses `~/.config/agent-notes/signing.key`. The `Path` import is slightly messy — it's imported inside methods rather than at module top, which is a defensive pattern for optional deps but looks a bit unusual.

What I'd want a second pair of eyes on:
- The `parent_op_ids` field in `commit_op` is currently set to `[entity_id]` for update ops. This is a simplistic parent chain. For P2 (merge), the parent chain needs to be the actual set of ops that haven't been merged yet. The current code is sufficient for P0 single-writer but will need a rewrite for multi-writer.
- The `wi_status_changed_fn` trigger is a copy of `bc_status_changed_fn`. It's correct but duplicative. The plan says this is a migration concern, but having two nearly identical triggers is a smell. Not worth fixing in P0, but worth flagging for the migration PR.
- The `agent_notes` CLI is now quite large. The `__init__.py` imports 12+ parser modules. This is fine for now, but the registration pattern is growing. A plugin system (entry points) might be needed before P3.

## On what remains

P0 is done. The next phases are:
- **P1 — enforcement on:** Standalone verifier CLI (DSSE sigs + hash chain + OPA/Rego policy). This needs the `cryptography` package as a real dependency (not optional), and the `verify_envelope` function in `envelope.py` needs to be wired into a CLI command.
- **P2 — merge / reconcile:** Deterministic merge, fail-safe status lattice. This is the keystone. The prerequisite is reading Radicle `issue.rs` status-merge rules first. The `fold_work_item` function needs to handle concurrent ops and the status lattice. `parent_op_ids` needs to be the actual set of unmerged ops.
- **P3 — cross-project:** Registry + index + `project:identifier`. This needs the `links` table to carry cross-project edges, which it already does (decision 14). The `request` / `wait` ops need to be implemented and the intake flow materialized.
- **P4 — full multi-agent:** regista coordinator (atomic claim/lease/heartbeat), degrade contract, `requeue_expired`, causal-stability watermark. This is the heavy coordination layer.

Not needed before P0 ships:
- Breadcrumb → work-item migration. The plan explicitly says this is its own PR before P0 or as the first commit of P0 with its own test plan. The existing `breadcrumbs` table is untouched.
- The `op_log` does not replace `change_log` yet. Both tables exist. The `change_log` trigger is still the NOTIFY source.

## Gaps to flag

- **Missing test:** `test_work_items.py` does not test `suggest_duplicates`. The function exists in `WorkItemModel` but is untested. Copy the breadcrumb duplicate tests.
- **Missing test:** `events_since` with a non-zero cursor. The current test (`test_events_since`) starts from cursor=0. Testing with a partial cursor would verify the tail behavior.
- **Schema drift risk:** `content_blobs` stores the body text as `TEXT`. For very large bodies (e.g., 10MB logs), this could be a problem. The schema should be watched; if bodies grow, switch to `BYTEA` or a separate storage backend.
- **Dead code:** `cmd_bc_query` in `cli/breadcrumbs.py` is a strict subset of `cmd_bc_find`. This is already filed as **BC-018** (opened 2026-05-26). The work-item CLI doesn't have a `query` subcommand — it was intentionally skipped to avoid repeating the mistake.
- **Silent failure mode:** `WorkItemModel.file_work_item` with `identifier=None` calls `allocate_work_item_identifier`, which uses `FOR UPDATE` on the sequence table. If two calls race (concurrent writers), the second might block. P0 is single-writer, so this is fine. P4 needs the coordinator for atomic claim.
- **Formatting drift:** Some files (`src/agent_notes/cli/common.py`, `src/agent_notes/cli/export.py`, etc.) show as modified in `git status` because of prior `ruff format` runs. These are whitespace-only changes. They should be committed with this session's work or reset to avoid cluttering the diff.
